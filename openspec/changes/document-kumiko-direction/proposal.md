# Proposal

## Why

Kumiko needs a durable record of the product direction established in exploration: a Flutter agentic development environment connecting human-and-agent conversations, planning, and development work across Windows, Linux, and macOS. Capture the agreements now so continued discussion does not confuse accepted decisions with recommendations or turn an unfinished exploration into an implementation commitment.

## What Changes

- Record the intended product behavior in capability specs, with the discussed architecture and decision status in `design.md`. These describe a product to build; they are not claims of implemented functionality.
- Support standalone solo work without a team server or account, and an optional shared, self-hosted team deployment. Shared records require the server; local development remains available when disconnected. Offline synchronization is excluded from the initial design.
- Open first launch directly in Personal for local terminals/configured agents without a mandatory account, project, wizard, or team connection. Offer Create project and Connect to team server without blocking local work. Team connection identifies the server/team and uses its configured sign-in; failures leave local work usable and never migrate private sessions or solo projects.
- Have the operator explicitly designate a new self-hosted deployment's first administrator during server setup, never through a first-login race. Later administrator appointments require an explicit action by an existing administrator; sign-in alone grants neither that role nor project membership.
- Negotiate client/server protocol, data-contract, and capability support rather than require matching release versions. Client-first upgrades retain existing functionality against the older server; server-first upgrades continue serving older clients through backward-compatible protocol and schema contracts. Server-dependent additions remain unavailable until both peers support them.
- Notify desktop users when an update is available and install it only after explicit user consent; availability or notification interaction alone must not trigger installation. If an update requires interrupting agents or terminals, identify the affected work and wait for explicit consent to stop it; installation consent alone does not authorize interruption.
- Treat a project as a coordinated effort across applications/repositories, with freeform work rather than an execution pipeline. Include task types, priorities, labels, assignees, dates, custom fields, templates, dependencies, discussions, saved list/board/timeline views, milestones/roadmaps, optional cycles, dashboards/statistics, documents/notes, estimates, and time logging.
- Provide project-configurable task statuses with Backlog, To do, In progress, Blocked, and Done defaults. Support arbitrarily nested independent subtasks: direct children in task details, flat overview records with parent navigation, and a distinct Done warning/count for unfinished descendants without automatic completion or reopening.
- Reparent within a project without breaking descendant relationships or changing task identity, status, assignee, dates, milestone associations, or history; reject circular or stale moves. Archive only the selected task by default, leaving children available with their archived parent identified. Delete only the selected task by default, promoting direct children to its former parent or top level while preserving deeper relationships. Whole-subtree archive/delete requires explicitly named scope, affected-task count, and confirmation; nesting alone never authorizes a cascade.
- Preserve status identity and task associations when renaming, recoloring, or reordering. Remove an unused status without changing tasks; removing an occupied status requires an explicitly selected valid same-project replacement, affected-task count, and confirmation before migration/removal. Invalid or concurrently changed configuration rejects the stale request without dangling status references or an implicit fallback. Status settings never delete tasks or erase their change history.
- Let projects use only basic tasks/list/details by disabling optional planning features. Enforce sensible prerequisites through UI/API/tools; disabling dependent features requires confirmation, preserves data, and permits re-enabling. Calendars show dated work only; email, meeting scheduling/invitations, and external calendar synchronization are excluded.
- Use full, responsive task-detail/creation tabs with content, compact internal properties, direct subtasks, linked work, and discussion/history. Create explicitly with title as minimum input; commit property selections immediately, but save/cancel prose explicitly and post comments explicitly. Keep unfinished text/comment drafts local, preserve failed/conflicting edits, show honest save state, and require server confirmation for shared writes without an offline queue.
- Protect task fields and app-owned document/note/project-instruction text from stale writes through UI, APIs, and agent tools. Task updates touch only submitted fields: independent field changes survive, while stale same-field writes reject without losing the saved or attempted value. Inspect current text alongside the draft, reconcile manually, and explicitly save again with an intervening-change check; no initial live coediting or automatic merge. Clean views refresh without replacing unfinished edits. Failed/conflicting drafts remain owner-local across app restart, never auto-publish, and explicit discard prevents recovery. Borrow useful editing patterns, not ItsAPlan's source, blur-saving, or same-field last-write-wins behavior.
- Provide flat task lists and status-column boards, date-only timelines and month calendars, consistent navigation/committed edits, and personal-by-default saved views with explicit project publication and definition updates. Dates do not imply midnight or timezone shifts; scheduling does not automatically move related work.
- Provide clickable milestone-by-milestone roadmap status, completion counts/percentages, date-only targets, and full outcome/task details. Explicit milestone closure records delivered/partial/unachieved outcomes and remaining work without forcing task completion or 100%. Tasks can exist/work outside the roadmap, move to Later or a later milestone, or leave the roadmap without duplication/deletion/history loss.
- Start and finish optional cycles explicitly; an elapsed end date never silently finishes one or starts another. Allow confirmed closure with unfinished work after showing finished/unfinished counts, without claiming an unfinished goal achieved. Retain task links and independent fields by default. Carry-forward separately selects unfinished tasks and destination, shows the affected count, and requires confirmation; move existing records without cloning, preserve prior cycle association in history, and never include subtasks merely because their parent moves.
- Let deferred/canceled inclusion toggles change both visible work and completion counts/denominator consistently in roadmap and milestone details, never milestone status or recorded outcome. A Done milestone with 8 completed and 2 deferred tasks displays 80% (8/10) when included or 100% (8/8) when excluded, with excluded work indicated.
- Keep personal development on the user's PC: private coding-agent conversations, terminals/output, checkouts, local branches/edits/files, and personal working layouts are not uploaded, synchronized, indexed, or exposed through the team server, including to administrators. Shared projects, tasks, project chats, documents, and project activity remain the collaboration boundary. A task/session association is not transcript, terminal, or working-copy publication; explicit Git/integration publication and selected AI-provider requests remain separate operations.
- Provide a three-zone workbench: joined projects/workspaces and global My tasks/Needs attention on the left; independently tabbed and split working views in the middle; contextual Files, Sessions, SCM, PRs, and Tasks on the right. Details, creation, and editing open as full main-area tabs. Direct project/workspace clicks restore personal working layouts without stopping work or retargeting existing sessions.
- Make terminal-native CLIs and structured Chat UI equally first-class. Both sidebars can collapse independently without changing splits or sessions; hiding them is optional, not a terminal-use mode. Allow immediate projectless work in a local Personal working set without creating a project, repository, or team account. Use a visible, labeled + launcher in each tab group; exclude embedded browser and mobile emulator from the first functional release.
- Use existing Claude Code, Codex, and OMP runtimes through adapters, with freeform chat-driven work and owner-controlled authority. Each user has a personal locally running read-only chat agent that can inspect accessible local code and authorized project context, explain findings, and suggest improvements privately. This role cannot modify code or Git, execute local work, update tasks, publish externally, or delegate those writes, even on owner request. Shared/project-owned discussion agents are outside initial scope; separate coding agents retain their authorized capabilities.
- Use the runtimes' existing authenticated AI accounts without managing provider sign-in, credentials, subscriptions, or billing. Surface supported model/effort choices, commands, and skills; provide detailed token/cost statistics with clear source coverage and estimated-cost labels.
- Keep saved agent conversations resumable through owner-local Sessions history, not through guaranteed process survival. Closing an idle agent chat is immediate; closing a working agent asks before stopping it. Terminal tab/pane closure warns before terminating affected processes. Stop-in-chat remains a supported turn interruption, distinct from confirmed close; neither deletes saved history or undoes completed file changes.
- Preserve unsent message drafts locally per conversation across navigation, tab closure, and app reopening, never on the team server or automatically sent. Shared-project sending still requires current server access.
- Provide optional versioned Project settings > Agent instructions, separate from reference documents and additive to native setup. Show selected guidance and project/workspace at launch. Existing sessions retain their adopted revision; a quiet update indicator lets only their owner inspect and explicitly apply changes without interruption or silent queuing. Distinguish available, selected-for-delivery, and adapter-confirmed delivered guidance.
- Prepare selected text, files, tasks, and documents as visible previewable/removable context attachments in an explicitly identified conversation draft; only Send delivers them. Selected text retains its source/revision/range and unsaved label without saving the file. Flag pre-send source changes, retain the snapshot until explicit refresh, and never retarget drafts on navigation or treat context as instructions or permission grants.
- On whole-app exit, preserve open windows/tabs/panes, split layout, and saved agent-session associations for reopening. Idle/saved exit needs no unnecessary prompt; active work and unsaved files require individual decisions or an explicitly labeled bulk stop-processes/discard-file-edits exit. Failed saves retain edits and block ordinary exit unless subsequently discarded. Explicitly discarded file drafts must not return through recovery. Restore terminal layout, not Vim/lazygit or previous commands. Tmux-style process persistence is deferred.
- Start in the current checkout. Provide workspace-aware Git controls in a dedicated right-side SCM panel, including current-branch pull requests; defer jj and GitButler integration.
- Review changed-code diffs centrally from SCM and collect user-authored local line/range comments, not source-file comments or project notes. Explicitly send collected feedback to the selected private coding chat; adding notes alone does not instruct or interrupt an agent or publish anything.
- Preserve review notes and original code excerpts with workspace/file/revision/range. Flag changed or unverifiable anchors, expose reviewed and current code separately, and never infer resolution from edits. Allow explicit sending of older feedback with its original context and warning; re-anchoring requires deliberate user action, not guessed relocation.
- Provide one attention-notification history through a small global top-bar Notifications button, with Needs attention as its active undismissed pending subset. Distinguish seen, dismissed, and source pending/handled states. Dismiss only the notification with a clear explanation, never the request. Never remind or repeat an unchanged request; keep readable agent status visible independently.
- Show only minimal generic desktop attention alerts while Kumiko is unfocused/minimized, without private previews or focus stealing. Clicking opens the authorized source without answering, approving, or resolving anything. Retain dismissed/handled notifications in accessible history; routine activity is not notification-worthy and email notifications remain excluded.
- Provide one global quick-open/search surface for accessible projects, tasks, documents, conversations/agent sessions, and execution workspaces. Identify each result's context; keep file search scoped to the selected execution workspace and shared content dependent on the team server.
- Provide shell-agnostic terminals and lightweight Markdown/configuration-first editing, not a full IDE. Workspace files use explicit Save: clean buffers follow agent/external disk changes without save prompts; unsaved edits survive navigation and prompt on close. Keep recovery drafts owner-local, restore them without writing the checkout, and warn before retained edits overwrite external changes. No automatic merge editor is required. Record accepted editor component choices and the still-unqualified terminal candidate in the design.
- Provide a T3-style Open in button/menu with user-configurable applications, not only editors. Include VS Code and Zed presets and allow users to add other programs for the active workspace or selected file.
- Own project documents in Kumiko, stored locally for solo projects and on the server for team projects. Keep repository documents separate, and make documents discoverable through permissioned agent tools rather than injecting the whole library into every prompt.
- Package backups as ZIP containing a database dump of eligible Kumiko-owned records plus any externally stored owned attachments; database-resident attachments need no separate payload. Preserve repository, agent-setup, agent-conversation, and credential exclusions even when colocated. Use no custom archive format or built-in password/encryption feature; retain basic integrity/version checks before restore changes current data. Restore replaces the selected datastore's eligible data with the backup, never merging older and current records. Identify backup and destination, warn that changes since the backup will be lost, and require explicit confirmation before replacement. Restore does not recreate the working environment.
- Retain project records without automatic expiry initially; default to archive, with separate confirmed permanent deletion limited to Kumiko-owned records. Solo owners control their own project lifecycle; team project archive requires its lead or team administrator, and permanent deletion requires its team administrator. Do not cascade deletion or rewrite other projects' referencing records; show targets as Deleted or unavailable without readable fallback copies. Private agents/terminals continue untouched; deleted-task writes fail without recreating tasks.
- Keep solo database backup/restore under the local owner's authority over local data only. Team-server database backup/restore belongs to the deployment operator through server administration, not ordinary project controls or automatic Kumiko administrator entitlement. The same person may hold both responsibilities independently. Agent tools enforce the initiating owner's operation permissions; instructions and confirmations cannot confer missing authority or bypass backup validity checks.
- Link GitHub/Jira work to native tasks and fetch source details and comments without two-way field synchronization or automatic comment mirroring. External publication is a distinct, explicitly authorized action.
- Support configurable enterprise SSO and public/self-hosted integration targets, while keeping Kumiko login, external API credentials, and machine-execution permissions separate. Sign-in methods attach to or create internal Kumiko accounts; account roles and project memberships determine application access, not the sign-in provider.
- Let normal team users create projects and become their initial member and lead without self-invitation; other normal users join through accepted invitations. Project leads can invite within their project. Keep two account roles: normal user and administrator. Administrators can see and participate in every project within their team and manage access/invitations without being its lead, but the sidebar lists only projects the user belongs to. Provide simple server/tool-enforced access administration in the first finished release; defer a separate project browser and join requests. Project authority never exposes personal development resources; solo projects have no team invitation gate.
- Bind project invitations to the intended internal account, with separate in-app pending invitations, visible server/team/project/inviter/expiry, explicit Accept/Decline, and a manually shareable link that grants nothing by itself. Require an account established under the deployment's rules; no email service is required. Invitations expire, can be revoked by administrators, cannot duplicate membership or restore revoked access, and replacements require separate acceptance; exact expiry duration remains undecided.
- Enforce revoked normal membership on subsequent shared reads/writes, existing subscriptions, and agent tools. Once known, replace restricted open views with Project access removed and remove membership navigation and shared search/attention results. Preserve private agents, terminals, checkouts, files, conversations, and unsent local drafts; block unauthorized sending and automatic resend after restoration. Do not claim rollback of committed operations or retraction of already-read/model-sent content. Removing administrator project membership changes membership/sidebar, not the separate team-wide administrator role.
- Keep at most one designated project lead, reassigned explicitly by an administrator to a current member without bypassing invitation acceptance. Former leads remain members unless separately removed; reassignment does not move tasks, assignees, private agents, or checkout ownership. Membership removal clears the lead designation without delaying revocation; a visible vacancy does not block project use. Lead responsibility alone cannot appoint a successor.
- Require current team-administrator authority and explicit target/account/team/resulting-role confirmation for promotion or demotion. Server enforcement must prevent zero administrators, including concurrent changes; self-demotion requires another administrator to remain. Demotion preserves ordinary memberships but removes administrator-only operations and unjoined-project access from existing sessions without touching private work or auto-joining projects. Lockout recovery requires separate deployment-operator control; its concrete mechanism remains undecided.
- Do not gather client product telemetry or crash/error reports. Offer telemetry-free builds that exclude collection/upload components entirely and provide no option to enable them; local token/cost statistics and authorized agent/integration traffic are separate concerns.
- Keep diagnostics minimal and operational: timestamps, component/version, operation type, duration, and structured error codes, not user-activity tracking. Exclude prompts/replies/drafts, document/file/diff contents, terminal output, tool arguments/results, credentials, and secret-bearing connection data; raw third-party errors are not inherently safe. Desktop logs stay on that PC; server logs cover server operations without private desktop activity or shared message/document bodies. Automatically rotate diagnostic logs within finite bounds independently of project-record and saved-conversation retention. Support explicit inspection and local offline diagnostic-bundle export only, with no automatic attachment, sending, or upload. Exact retention limits and export format remain undecided.
- Connect agents to a local Kumiko MCP service automatically: qualified runtime injection when supported, otherwise merge repository-scoped registration in the runtime's native format. Do not assume universal `.mcp.json` discovery.

## Capabilities

### New Capabilities

- `work-planning`: coordinated projects, independent nested tasks and safe hierarchy operations, stable statuses/migration, protected saves/local failed-draft recovery, saved views/date-only planning, milestone outcomes/optional roadmap placement, completion toggles, explicit cycle closure/confirmed selective carry-forward, and modular planning.
- `collaboration-deployment`: Personal-first optional onboarding/team connection, independent local work, shared team state, disconnection/reconnection, mixed-version compatibility, and consent-controlled desktop updates.
- `enterprise-identity`: configured sign-in/internal accounts, explicit administrator establishment and confirmed team-scoped role changes, last-administrator safety, operator-controlled recovery boundaries, and separation from project/integration/host authority.
- `project-access`: creator membership, administrator-controlled member-only lead reassignment/vacancies, invitation lifecycle, live revocation/demotion, preserved private work, lead-or-administrator project archival, administrator-only project deletion, and account/project authority distinct from deployment operations.
- `workbench-layout`: project/Personal working sets, full tabs/splits, task/planning screens and milestone drill-down, contextual tools, optional sidebars/launcher, global notification history with persistent agent-status indicators, and app-exit restoration/stop/discard decisions.
- `agent-sessions`: capability-aware runtimes, owner-local conversations/drafts/history and supported resume, explicit close/interruption/recovery, and destination-bound visible context attachments with deliberate Send and selected-text snapshots.
- `discussion-authority`: personal locally running read-only chat agents, authorized local-code/project-context inspection, private findings and suggestions, no initial shared agents, and no code/Git/task/publication writes or delegated bypasses.
- `execution-workspaces`: selected-checkout execution, explicit workspace creation, and host-scoped authority.
- `source-control`: workspace-aware Git controls and branch-linked PRs, plus local diff comments, preserved reviewed excerpts, changed-context warnings, deliberate re-anchoring, and explicit private-chat revision requests.
- `terminal-sessions`: first-class shell-agnostic and terminal-native agent use without project or Chat UI requirements, process-loss confirmation on close, layout-only reopening without application/command replay, and no team streaming.
- `workspace-editing`: lightweight workspace browsing, Markdown/configuration-first editing, explicit saves and close prompts, clean external refresh, owner-local draft recovery and visible external conflicts, and configurable Open in applications.
- `project-documents`: optional Kumiko-owned document libraries and notes, canonical Markdown, access/revisions/discovery/export independently of Tasks, and explicit text saves with conflict preservation, manual reconciliation, and owner-local failed-draft recovery.
- `external-work-links`: linking GitHub/Jira items, retaining independent lifecycles, fetching activity, and explicit publication.
- `agent-tool-access`: native setup preservation, scoped tools and adapter-specific MCP setup, versioned project guidance with protected text saves/local failed-draft recovery, and separate owner-controlled session adoption with truthful delivery state.
- `attention-inbox`: cross-project attention/history, independent seen/dismissed/source state, notification-only dismissal, no unchanged-request reminders, minimal background-only desktop alerts, safe source navigation, owner-local privacy, and no email notifications.
- `global-navigation`: unified quick-open across work objects, contextual result identity, and workspace-scoped file search under existing access and connectivity rules.
- `agent-usage`: observational token/cost statistics, supported runtime/session breakdowns, source coverage, and honest separation of reported usage, estimates, and subscription billing.
- `data-lifecycle`: eligible ZIP backups/checks/no built-in encryption, confirmed replacement-only restore with backup/destination and data-loss warning, local-owner versus deployment-operator authority, role-bound project archive/deletion, unavailable references without cascades, private-work preservation, initial record retention, and bounded diagnostic logs.
- `product-telemetry`: no client product-telemetry/report gathering or runtime-enableable collectors in telemetry-free builds; minimal operational diagnostics with content/credential exclusions, desktop/server ownership boundaries, and inspected offline local export without uploading.

### Modified Capabilities

None. There are no existing main capability specs.

## Impact

Planning artifacts only: this proposal, `specs/<capability>/spec.md`, and `design.md` under this change. No application code, dependency installation, schema changes, repository MCP configuration, review artifact, implementation tasks, or runtime qualification is included.

The change remains open as a living exploration record. Its design distinguishes **agreed decisions**, **proposed defaults not yet approved**, **deferred scope**, and **unverified assumptions / required qualification**. As the remaining points are discussed, update these same artifacts within the approved capture scope; do not infer acceptance from silence. Formal implementation planning and project-level strategy/architecture/roadmap artifacts are not authorized by this capture.
